Camera-off sessions keep the time worked while the phone was locked NEW
PR: #585 · Agent: Cloud Agent · Status: Waiting for your review (draft PR, merges cleanly, not merged)
Reported by: Ace (@1ace) in Discord #general-chat, Oct 22, 5:48 AM PT (“it was 1hr 11min 29s / instead it got logged as 1min 29s”, build 1.0.7 (41)). PostHog: the same thing happened 23 times to about 20 people in the last week (builds 1.0.7 and 1.0.8), about 12 hours lost in total.
What was wrong and what changed: When someone records with the camera off and locks the phone, Latent keeps timing. When the phone is unlocked into another app, Latent waits 8 seconds to tell a quick Lock Screen glance from really leaving, then pauses from the moment of the unlock. But iPhone often puts Latent to sleep during that wait, so when it woke up much later it treated the whole locked stretch as time away and kept only the minute or so before. That is how Ace's 71 minutes became 1 minute 29 seconds. Now, if the wait ran late, the pause starts when Latent actually notices, so the locked time stays as worked time, it rechecks the Lock Screen first so a glance still doesn't pause (#511), and it never counts more than the real clock. It also logs two new fields so PostHog can show if it ever happens again.
How to check: On a phone (the simulator can't lock): start a camera-off (Photo + timer) session, lock the phone for 10+ minutes, then unlock straight into another app (not through the Latent Lock Screen widget), wait about a minute, open Latent and finish. The saved time should be about 10+ minutes, not about 1 minute. Also lock, tap the Live Activity on the Lock Screen without unlocking and put the phone down: the session should keep running with no stuck “Session paused”. The agent couldn't compile (no Mac), so run RecordClockTests on a Mac first.

Saves retried when you reopen the app no longer go out as if you're signed out FROM OCT 20
PR: #568 · Agent: Cloud Agent · Status: Still waiting for your review (draft PR, merges cleanly, not merged)
Reported by: PostHog (session_save_failed “permission denied for table work_types”, the server saw a signed-out visitor). 6 people in the week before Oct 20; 2 more people in the last day (builds 1.0.8 (43) and 1.0.7 (41)). Opened by the Oct 20 dig.
What was wrong and what changed: When someone saved a session and then left the app for about an hour, the save that retries as the app reopens could go out before the app had signed the person back in. The server treated it like a logged-out visitor and refused it (“permission denied for table work_types”), so the post never reached the server and its video then got stuck. Now the app waits until the person is signed in again before sending, retries once if it is still refused, and never throws away the session or its video. A normal save without leaving the app works the same as today.
How to check: On a phone with this build: sign in, record a short session, save it (with a clip, shared with friends), then put Latent in the background right away and leave it for more than an hour. Reopen Latent: the post should still be on your profile, a friend should see it with a playable video, and PostHog should show no “permission denied for table work_types” save failure for that reopen. The agent couldn't compile it (no Mac), so it asks you to run the Mac tests and this phone check before merging.
